# acceptance-test：开发完 → 验收测试 → 一份完整报告

功能做完之后的收尾环节。**这个 skill 只管测试和出报告**——服务在此之前已经起好，
前端地址、DB 连接参数你自己从上下文拿得到，不用在这里操心环境怎么拉起。

从 `.workspace/workspace.env` 读 `BACKEND_DIR` / `FRONTEND_DIR`（不要写死项目名）。

## 产出形态

一个文件夹，默认落在 **工作空间根目录** 的 `reports/<name>/`（调用方指定了输出目录就用它给的）：

```
reports/<name>/
├── REPORT.html      # 浏览器中直接打开的报告入口
├── images/          # 截图原图
├── console.txt      # 失败时按实际采集情况保存
└── network.txt      # 失败时按实际采集情况保存
```

- `<name>`：调用方给的 slug；没有就自己从功能起一个短横线名（`^[a-z][a-z0-9-]*$`）。
- 同名重复跑 **直接覆盖**——报告反映"当前这次开发的最终状态"，不留历史版本。
- 报告使用相对路径引用证据。移动或分享时保留整个报告目录。
- **不要**把报告或截图写进 `BACKEND_DIR` / `FRONTEND_DIR` 里的任何位置。

## 输入（调用方传入，或你自己从上下文归纳）

| 项 | 说明 |
|---|---|
| 改动摘要 | 这次开发做了什么、目标是什么 |
| 改了哪些文件 | 文件清单 + 每处为什么改（独立运行时从 `git diff` / 对话上下文归纳）|
| 验收标准 | 逐条"能观察到什么现象就算这次做对了"，自然语言，不是"代码写完了"这种。调用方给了就用它的（实现中发现偏差以实际为准）；没给就依据改动和需求现拟 |

## 步骤

### 1. 建目录
`mkdir -p reports/<name>/images`

### 2. 后端测试
```
cd <BACKEND_DIR> && mvn -q test
```
关键行原样留进报告：`Tests run: X, Failures: 0, Errors: 0, Skipped: 0`。
有失败，贴出失败的测试类和断言消息，不要只写"有失败"。
（调用方已经跑过并把输出给你了，就直接用，不用重跑。）

### 3. 前端（仅当前端有改动，`git -C <FRONTEND_DIR> status --porcelain` 非空）
```
cd <FRONTEND_DIR> && pnpm install && pnpm typecheck && pnpm build
```
任一步失败贴报错。（同上，调用方给了结果就直接用。）

### 4. 可视化验证

**判据——这次改动有没有值得走一遍"真实浏览器 + DB 断言"的可观察行为：**

- **有** → 走下面。触发条件（满足任一）：新页面、改交互、改表单/校验、改数据绑定、
  后端改动影响了既有页面能观察到的行为（响应结构 / 权限点 / 列表详情字段 / 新端点被既有页面消费）、
  改了跨前后端的流程（登录、鉴权、分页、导出等）。
- **没有** → **跳过**。纯内部重构、仅文档注释、纯后端且 UI 上无任何可观察差异、仅测试代码。
  在报告的可视化验证一节写"本次跳过 —— <一句理由>"。

用当前可用的浏览器工具执行。浏览器工具只支持部分操作时，继续完成可执行的验证，并在报告中写明缺少的操作或证据。

1. **登录**：浏览器打开前端地址，优先使用调用方提供的验收账号和口令。使用本地 `dev-seed` 创建的默认 `admin` 时，按以下步骤取初始口令：
   - 优先查看当前后端实例的 `dev-seed` 启动日志，确认口令文件的绝对路径。没有相关日志时，检查该实例的 `describeadmin.system.dev-seed.password-file` 配置。未配置时默认为 `.passwd`，相对路径以启动后端的 JVM 的 `user.dir` 为基准，绝对路径直接使用。
   - 启动脚本或命令行启动时，查看实际的后端启动目录。用 IntelliJ IDEA 启动时，查看运行配置的 `Working directory`。如果它指向工作空间根目录，默认文件就在那里。只有 `user.dir` 指向 `<BACKEND_DIR>` 时，默认文件才位于 `<BACKEND_DIR>/.passwd`。
   - `dev-seed` 启用且数据库中没有用户时才初始化管理员。找不到对应的口令文件、无法确认初始口令仍有效或登录被拒绝时，向调用方获取当前验收凭据。口令仅用于登录，报告和截图不得包含口令。
   - 若落到"强制修改密码"页，说明该账号还没改过初始口令。
2. **按验收标准执行真实操作**：一步步走完流程。定位页面元素 **一律用 `[data-testid="..."]`**——
   没有 `data-testid` 的交互元素视为该功能"未完成"，不要退而求其次用文本 / xpath / class 选择器，
   那等于在帮它遮掩这个缺口。工具报找不到元素时，先怀疑页面没渲染完或快照过期，
   而不是怀疑 `data-testid` 写错（那应该读源码核实过）。
3. **每个关键步骤截图**：用当前客户端的浏览器工具截图，存到报告目录的 `images/step-NN-<简述>.png`。
4. **DB 断言**：用 `mysql` 查，**比对具体值**，不要只比 `COUNT(*)`——字符集配错时计数完全正常，
   中文却全写成乱码，只比行数发现不了。
   ```
   mysql -h127.0.0.1 -P<port> -u<user> -p<pass> --default-character-set=utf8mb4 \
     -N -B -e "<单条 SELECT，返回一行一列>" <schema>
   ```
5. **有副作用的场景收尾**：如果操作新增/改了数据，测完用 `mysql` 把它清回原状，保证可重复跑。
6. **出错**时，继续执行剩下可以运行的步骤和断言。有控制台或网络日志时，将它们保存为
   `console.txt` 和 `network.txt`。工具无法采集这些日志时，记录错误提示和可取得的现场证据。

### 5. 写 HTML 报告

- 将[报告模板](REPORT.template.html)复制为输出目录下的 `REPORT.html`。填写实际结果并替换所有示例内容。测试输出、日志片段及其他动态文本写入 HTML 时要转义。
- 每张截图放在对应操作下，写明它证明的现象。缩略图和原图链接都指向同一个 `./images/xxx.png`。点击缩略图在本页放大，按 `Esc` 或点「关闭」返回，点「打开原图」查看实际像素。日志仅在有对应文件时链接。
- 本地浏览器打开 `REPORT.html`，确认图片和日志链接有效。有截图时至少验证一张截图能打开、关闭和查看原图。报告使用模板内置的样式和脚本，直接打开即可阅读。
- 交付时链接到报告入口 `REPORT.html`。

### 6. 如实汇报
- UI 断言和 DB 断言 **都通过** 才算通过。只有 UI 通过、DB 没查或没通过 → 如实写"部分通过"。
- 浏览器自动化不可用 → 如实写"可视化验证未执行"+ 原因，**不要静默跳过**。
- 不因"页面看起来正常"就判定通过。

## 被 describe 调用时

`describe` 会在功能实现完、后端/前端测试跑完后调本 skill，并传入：改动摘要、改了哪些文件、
验收清单（取自它的 `notes/PLAN.md`）、输出目录（`<worktree>/reports/<slug>/`）、以及它已经跑出的
后端/前端测试输出（直接引用，步骤 2、3 不用重跑）。行为与独立运行完全一致，只是这几项不用你自己归纳。
任一断言失败 = `describe` 的阻塞结论。
